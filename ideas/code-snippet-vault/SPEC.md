# Code Snippet Vault — SPEC

**MVP:** A private, logged-in-only SaaS for saving and organizing code snippets. A user logs in via magic link, creates snippets (title, language, code, comma-separated tags), and sees them listed newest-first with client-side search (title/tags/code) and filters by language and tag. Every snippet is syntax-highlighted in the display. Delete is supported; edit is not (out of scope for this pass — see below).

**Syntax highlighting choice:** added `highlight.js` (`^11.12.0`, BSD-3-Clause) as a real npm dependency rather than a hand-rolled monospace-only display. It needs no build step beyond normal webpack bundling (verified the package's actual installed `types/index.d.ts` and `lib/index.js` before using it — `import hljs from "highlight.js"` gives a default export with every language pre-registered, and `hljs.highlight(code, { language, ignoreIllegals: true }).value` returns pre-escaped HTML). Rendered via `components/CodeBlock.tsx` (`dangerouslySetInnerHTML` on hljs's own escaped output — not raw user input). Styling for the emitted `hljs-*` token classes is a **hand-written theme in `app/globals.css`**, not one of highlight.js's bundled `styles/*.css` files — avoided importing a package's CSS from a nested Client Component because Next.js App Router's exact rule for where plain (non-module) CSS imports are allowed to resolve wasn't something to guess at; writing ~15 lines of custom CSS against the same design tokens as the rest of the app sidesteps the question entirely and looks visually consistent.

**Scope adaptations:**
- No editing an existing snippet — delete-and-recreate only. Real product would want in-place edit; cut for time, all the plumbing (RLS update policy, `updated_at` trigger) is already in `schema.sql` so adding an edit form later is additive, not a schema change.
- Search/filter is entirely client-side over the snippet list already fetched on page load (Server Component fetches all of the logged-in user's snippets once; the Client Component filters in memory). Correct and fast at demo scale (a handful to a few hundred snippets per user); would move to a server-side `ilike`/full-text query at real scale.
- No public/shareable snippets — every row is private to its owner via RLS, matching "private SaaS" in the one-liner.

**Schema (`schema.sql`):** one table, `code_snippet_vault_snippets` (`user_id` FK to `auth.users`, `title`, `language`, `code`, `tags text[]`, timestamps + an `updated_at` trigger). RLS: owner-only `select`/`insert`/`update`/`delete` (`auth.uid() = user_id`), no public read policy at all. GIN index on `tags` for future server-side tag search. Seed: 6 demo snippets (JS, Python, CSS, SQL) owned by a placeholder demo-user UUID — see the "Demo user note" comment block at the top of `schema.sql` for the exact steps needed once Supabase is live (the FK to `auth.users` means the seed `INSERT`s will fail until that user exists; this is expected).

**What still needs a live Supabase project to verify end-to-end:** the actual magic-link round trip (login → email → `/auth/callback` → session cookie), that the RLS policies behave as written under a real JWT (`auth.uid()` resolution), and that the seed data's demo user FK resolves once created. `npm run build`, `npx tsc --noEmit`, and `npm run lint` all pass clean locally with empty env vars.
