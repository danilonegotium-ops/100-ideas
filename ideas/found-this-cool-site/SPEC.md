# Found This Cool Site — SPEC

**MVP:** A "StumbleUpon" clone. The homepage loads the full pool of approved sites once (server-side, public — no login required to browse), then a "Surprise me" button picks a random entry client-side (avoiding an immediate repeat when the pool has more than one option) and shows it as a card: title (opens in a new tab), URL, short description, category tag. An optional category filter narrows the random pool before picking. Any logged-in user can submit a new site (title, URL, description, category) — auto-approved immediately per MVP scope (see below) — and can flag/report a link they land on as bad.

**Random-pick approach:** the full approved-sites list is fetched once server-side and picking happens in memory client-side (`Math.random()` over the current filtered array), not a `ORDER BY random() LIMIT 1` SQL query or a Postgres RPC. Correct and simple at this data volume (~30 seed rows, browsing/reporting won't add more than a handful at a time); would need to move to server-side random selection (or a cached ID list refreshed periodically) if the pool grew into the thousands, since fetching every row on every page load stops being cheap at that scale.

**Moderation scope adaptation:** the task explicitly asked for MVP simplicity here — submissions are **auto-approved** (`approved` defaults to `true`), not held for review. The `found_this_cool_site_reports` table exists and is fully wired up (insert-only from the client, a trigger keeps `sites.report_count` in sync automatically), but there is **no admin UI** to review flags or unpublish a reported site yet — reports just accumulate in the schema for a future moderation pass. RLS intentionally has no `select` policy on `reports`, so nobody (not even the reporting user) can read reports back through the anon/authenticated API — that data is for a future service-role-only admin tool, not the public app.

**Schema (`schema.sql`):** `found_this_cool_site_sites` (title, url, description, category, `submitted_by` nullable FK to `auth.users`, `approved` boolean default `true`, `report_count`) and `found_this_cool_site_reports` (site_id, `reported_by` nullable FK, reason, unique on `(site_id, reported_by)` so the same logged-in user can't inflate the count by reporting the same link repeatedly). RLS: sites are publicly readable when `approved = true`; inserting a site requires `auth.uid() = submitted_by` (must be logged in, must attribute it to yourself); reports insert requires `auth.uid() = reported_by`, no read access for anyone via the app API.

**Seed data:** ~30 real, currently-live, safe-for-work websites the author is confident about, spread across `tools` (9), `art` (5), `science` (6), `weird` (7), plus `music` and `learning` (1–2 each) for extra variety beyond the one-liner's three example categories. Two entries (Excalidraw, Shadertoy) are attributed to the placeholder demo user to demonstrate the submission relationship; the rest have `submitted_by = null` (curated pool entries, not user submissions) — see the "Demo user note" at the top of `schema.sql` for what to do about that placeholder UUID once Supabase is live. No invented/placeholder URLs — every seed entry is a real site.

**What still needs a live Supabase project to verify end-to-end:** that the RLS policies behave as written under a real JWT, that the `submitted_by`/`reported_by` foreign keys resolve once a real (or demo) user exists, and that the report-count trigger fires correctly. `npm run build`, `npx tsc --noEmit`, and `npm run lint` all pass clean locally with empty env vars.
