# Simple Uptime Monitor — SPEC

**MVP:** A logged-in user adds URLs to monitor (with an optional friendly label). A Vercel Cron job hits `GET /api/cron/check` every 5 minutes (`vercel.json`), which — using the Supabase **service-role** key (bypasses RLS, needed because a cron invocation has no logged-in user/session) — sweeps every monitor across every user, does a real `fetch()` against each URL, logs the result to a history table, and emails the monitor's owner via Resend **only when the status actually changes** (up→down or down→up), never on every check. A "Check all now" button on the dashboard lets you trigger the same logic on-demand for just your own monitors (via a second, session-authenticated route, `/api/check-now`) — useful for testing locally before Vercel Cron exists.

**Up/down definition:** a check is "up" if the request completes with HTTP status `< 400` (2xx/3xx, redirects already followed), "down" on any 4xx/5xx response, network error, or a 10-second timeout. Documented in `lib/uptime.ts`.

**Status-change tracking:** `simple_uptime_monitor_monitors.last_status` starts at `'unknown'`. The very first check for a new monitor just records that baseline status — it never sends an email (there's no "previous known state" to have transitioned from). Every check after that compares the new result to `last_status` before deciding whether to email; the email only fires on an actual value change, and `last_status` is updated on every check regardless of whether an email was sent.

**Email:** `lib/resend.ts` is a plain `fetch` against Resend's REST API (no SDK dependency). If `RESEND_API_KEY` is unset, it logs to the console instead of sending — the rest of the flow (checking, logging, status tracking) still works without it. Resend's sandbox sender (`onboarding@resend.dev`, the default `RESEND_FROM_EMAIL`) works without domain verification but — per Resend's own docs — can only deliver to the Resend account owner's own email until a real sending domain is verified; fine for demoing, worth knowing before expecting alerts to reach arbitrary user emails in production.

**Cron config — please double-check once live (per the task's explicit ask):**
- `vercel.json` at the idea root: `{"crons": [{"path": "/api/cron/check", "schedule": "*/5 * * * *"}]}` — every 5 minutes, matching the task's example. Vercel Cron always sends a `GET` request to `path`.
- **Known risk, unverified without a live Vercel project:** Vercel's Hobby (free) plan has historically restricted cron job frequency more than paid plans — worth confirming the current limit on whatever plan this deploys to once real Vercel access exists, since `*/5 * * * *` may get silently capped or rejected on Hobby. If so, the fallback is reducing frequency (e.g. hourly) or upgrading the Vercel plan — no code change needed, just the schedule string.
- **`CRON_SECRET`**: the route checks `Authorization: Bearer $CRON_SECRET` and returns 401 if it doesn't match — this is the officially documented way Vercel secures its own Cron invocations (Vercel auto-sends this header when it triggers the job, as long as a `CRON_SECRET` env var exists on the project). If `CRON_SECRET` is unset (true right now, and true in local dev), the route logs a warning and allows the request through unauthenticated — **must be set in Vercel's project env vars before deploying**, otherwise `/api/cron/check` is a public endpoint anyone could hit to force checks/spam emails across every user.
- **Execution time**: the cron sweep checks monitors sequentially, each with up to a 10s timeout — fine for a couple of demo monitors, but with many monitors the total sweep time could approach Vercel's serverless function duration limit. Not an issue at current seed-data scale; worth adding `export const maxDuration` and/or parallelizing with a concurrency cap if the real monitor count grows.

**Scope adaptations:**
- No per-monitor check-interval customization — every monitor is checked on the same global 5-minute cadence.
- No "manual check" for a single monitor, only "check all of mine" — kept it simple; the route already loops per-user, so scoping to one `monitor_id` would be a small additive change later.

**Schema (`schema.sql`):** `simple_uptime_monitor_monitors` (owner, URL, label, `last_status` enum `unknown|up|down`, `last_checked_at`) and `simple_uptime_monitor_checks` (append-only history: status, HTTP status code, response time, timestamp). RLS scopes both tables to the owning user for normal session access (dashboard, `/api/check-now`); the cron route bypasses RLS entirely via the service-role key, which is exactly what it needs to sweep every user's monitors. Seed: 2 demo monitors (one `up`, one `down`) with ~8 historical check rows, owned by a placeholder demo-user UUID — see the "Demo user note" at the top of `schema.sql`.

**What still needs a live Supabase + Vercel + Resend to verify end-to-end:** the actual cron trigger firing on schedule, `SUPABASE_SERVICE_ROLE_KEY` + `auth.admin.getUserById` resolving a real owner email, a real Resend send landing in an inbox, and the two cron-frequency/`CRON_SECRET` items flagged above. `npm run build`, `npx tsc --noEmit`, and `npm run lint` all pass clean locally with empty env vars.
